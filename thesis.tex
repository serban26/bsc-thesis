\begin{abstract}
Traffic load balancing is one of those problems that sounds simple until you
actually try to implement it properly. Spreading incoming requests across multiple
servers is easy in theory --- just take turns --- but doing it in a way that adapts
to real conditions requires visibility into the network that traditional load balancers
simply do not have.

This thesis explores an approach based on Software-Defined Networking (SDN).
By implementing the load-balancing logic inside a programmable network controller,
we get direct access to active flow counts, port statistics, and per-server health
metrics in real time. The controller intercepts every new TCP connection, picks a
backend according to the active algorithm, and transparently rewrites packet headers
in both directions so the client never has to know which server it is actually talking to.

We implement and compare two algorithms: \textbf{Weighted Round Robin} (WRR),
which distributes connections in a fixed cyclic order regardless of server state, and
\textbf{Least Connections} (LC), which always selects the server with the fewest
active flows relative to its weight. The system is built on Ryu~\citep{ryu2023},
Mininet~\citep{lantz2010mininet}, and Open vSwitch~\citep{pfaff2015ovs},
using OpenFlow~1.3~\citep{of13spec} as the control protocol.

To make the comparison meaningful, the three backend servers are given distinct
processing-time profiles and link-level delays, producing clearly different response
time distributions. The controller logs per-server metrics continuously, and a set of
Python scripts generates plots automatically at the end of each experiment.

Results show that both algorithms distribute traffic correctly and that the server
profiles produce the intended latency variation. The full comparison under concurrent
load is left as future work, along with an adaptive score-based algorithm that uses
all collected metrics together.

\bigskip
\noindent\textbf{Keywords:} Software-Defined Networking, OpenFlow, load balancing,
Ryu, Mininet, round robin, least connections, network emulation.
\end{abstract}

\section{Introduction}
\label{sec:intro}

\subsection{Motivation}

When a web service gets popular, one server is never enough. The standard solution
is to put multiple servers behind a single address and distribute the incoming requests
across them. The component that does this --- the load balancer --- is a surprisingly
interesting piece of networking infrastructure, because it has to make per-connection
decisions at high speed while keeping track of which backends are actually available
and how loaded they are.

The two most common traditional approaches are DNS-based load balancing and dedicated
hardware appliances. DNS-based balancing works by returning different server addresses
for the same hostname, spreading clients at the DNS level. It is simple and requires
no special network equipment, but it is inherently coarse: DNS responses are cached,
clients cannot be redirected mid-session, and the balancer has no visibility into actual
server load. Hardware appliances are more capable but are expensive, opaque, and
difficult to modify.

Software-Defined Networking (SDN) offers a different perspective. The central idea is
to separate the \emph{control plane} --- the logic deciding where traffic goes --- from
the \emph{data plane} --- the equipment that actually forwards it
\citep{mckeown2008openflow, kreutz2015sdn}. The control plane runs as software on a
standard server (the SDN controller), and the switches become programmable forwarding
elements that execute rules sent by the controller via a standardised protocol (OpenFlow).

This architecture is a natural fit for load balancing. The controller sees every new
flow, can read real-time statistics from switches, and installs per-flow rules that
rewrite packet headers on the fly \citep{handigol2009openflow_lb, zhou2014sdn_lb}.
Changing the scheduling algorithm means changing a few lines of Python --- no hardware
involved.

\subsection{Project Overview}

This thesis describes the design and implementation of an SDN-based HTTP load
balancer. The emulation stack consists of three open-source components:

\begin{itemize}
\item \textbf{Mininet}~\citep{lantz2010mininet} --- creates virtual hosts and links
  on a single Linux machine using network namespaces.
\item \textbf{Open vSwitch (OVS)}~\citep{pfaff2015ovs} --- a software OpenFlow switch
  that executes flow rules and reports statistics.
\item \textbf{Ryu}~\citep{ryu2023} --- a Python SDN controller framework.
\end{itemize}

The system exposes a single \emph{Virtual IP} (VIP, \texttt{10.0.0.100}) to the client.
The controller intercepts each new TCP connection, picks a backend, and installs a
bidirectional pair of OpenFlow rules that rewrite headers transparently. Neither the
client nor the servers require any modification.

Two scheduling algorithms are implemented: \textbf{Weighted Round Robin} selects
servers in a fixed cyclic order, oblivious to load. \textbf{Least Connections}
always selects the server with the fewest active connections relative to its weight.
Comparing them on heterogeneous server profiles is the central question of this work.

\subsection{Research Questions}

\begin{enumerate}
\item Can an SDN controller implement transparent HTTP load balancing without
  any changes to client or server code?
\item Is there a measurable difference in how Round Robin and Least Connections
  handle backends with different response time profiles?
\item What metrics does the controller need to make that comparison meaningful?
\end{enumerate}

The first question has been answered. The infrastructure for questions 2 and 3 is
fully in place; full comparative analysis under concurrent load is future work.

\subsection{Thesis Structure}

Section~\ref{sec:methods} covers system design. Section~\ref{sec:setup} describes the
experimental setup. Section~\ref{sec:results} presents results. Section~\ref{sec:discussion}
discusses them. Section~\ref{sec:conclusion} concludes.

\subsection{Controller Design}

The Ryu application (\texttt{controller/load\_balancer.py}) handles two OpenFlow
event types.

\paragraph{PacketIn.}
When no flow rule matches an incoming packet, OVS sends a PacketIn to the controller.
For ARP to the VIP, the controller replies directly. For TCP/UDP to the VIP, it calls
the algorithm and installs two flow rules:

\begin{itemize}
\item \textit{Forward}: (src\_ip, VIP, proto, sport, dport) $\to$ rewrite dst to
  backend; forward on server port.
\item \textit{Reverse}: (server\_ip, client\_ip, proto) $\to$ rewrite src back to
  VIP; forward to client.
\end{itemize}

Both carry \texttt{OFPFF\_SEND\_FLOW\_REM}, idle timeout \SI{2}{s}, hard timeout
\SI{60}{s}. A deduplication cache (\texttt{\_pending\_flows}) maps each 5-tuple to
the server already picked, preventing a race where OVS sends multiple PacketIn events
for the same TCP handshake before the FlowMod commits ($\approx$\SI{1}{ms}). Without
it, successive segments could be routed to different backends, breaking the connection.

\paragraph{FlowRemoved.}
When a flow's idle timer fires, OVS sends a FlowRemoved event with byte count, packet
count, and duration. The controller decrements \texttt{active\_conns}, updates
counters, updates the EWMA of flow duration, and writes a \texttt{flow\_removed}
record to the JSONL log. Figure~\ref{fig:flow} shows the full request lifecycle.

\subsection{Load-Balancing Algorithms}

Both algorithms subclass \texttt{LoadBalancingAlgorithm} and are registered in a
central registry, selectable via the \texttt{LB\_ALGORITHM} environment variable
(Strategy pattern).

\subsubsection{Weighted Round Robin}
A cursor advances through the server list one step per request. For weight $w > 1$,
a server is picked $w$ consecutive times before the cursor moves. The algorithm never
reads any metric --- it is fully oblivious to current load. Predictable and simple, but
cannot adapt.

\subsubsection{Least Connections}
At each selection, a weighted load is computed for every backend:
\begin{equation}
  \ell_i = \frac{\text{active\_conns}_i}{\max(w_i,\,\varepsilon)}, \quad \varepsilon = 0.01
  \label{eq:lc}
\end{equation}
The server with minimum $\ell_i$ is chosen; ties broken uniformly at random.
Under sequential traffic all servers reach $\ell_i = 0$ at each arrival, so LC
reduces to random selection. Its advantage is only realised under concurrent load,
where slow servers accumulate connections and LC routes around them while RR keeps
sending on schedule.

\subsection{Metrics Collection}

Each backend has a \texttt{ServerMetrics} object (Table~\ref{tab:metrics}). EWMA
smoothing ($\alpha = 0.3$) is applied to throughput, connection rate, and flow
duration.

\begin{table}[t]
\centering
\caption{Per-server metrics tracked by the controller.}
\label{tab:metrics}
\begin{tabular}{lll}
\toprule
\textbf{Metric} & \textbf{Unit} & \textbf{Source} \\
\midrule
active\_conns     & conns  & FlowRemoved \\
total\_bytes      & bytes  & FlowRemoved \\
total\_packets    & pkts   & FlowRemoved \\
throughput\_bps   & bit/s  & PortStats (EWMA) \\
conn\_rate\_eps   & conn/s & select() (EWMA) \\
avg\_flow\_dur\_s & s      & FlowRemoved (EWMA) \\
port\_errors      & count  & PortStats \\
selections\_total & count  & select() \\
\bottomrule
\end{tabular}
\end{table}

All metrics feed into a composite score for a future adaptive algorithm:
\begin{equation}
  s_i = \frac{c_i}{w_i} + 0.5\frac{q_i}{w_i}
      + 0.3\frac{\text{bps}_i}{10^7 w_i}
      + 0.2\frac{r_i}{w_i}
      + 2.0\,e_i + 0.2\,d_i + 0.01\frac{n_i}{w_i}
  \label{eq:score}
\end{equation}
Lower score = more desirable backend. The score is logged at every snapshot but not
yet used by any live algorithm.

Metrics are written to a JSONL file with events \texttt{select},
\texttt{flow\_removed}, and \texttt{snapshot}. A separate CSV records server,
status, and elapsed time per request.

\paragraph{Future improvements.}
A REST/Prometheus endpoint would allow external monitoring. The score weights are
currently hardcoded and could be tuned. An adaptive scheduler using
Eq.~\eqref{eq:score} in real time is a planned extension.

Combined with the link delays, the expected round-trip ranges are:
h2~$\approx$~35--45\,ms, h3~$\approx$~60--320\,ms, h4~$\approx$~90--340\,ms
(upper end during spikes). The 500 errors verify that the pipeline classifies them
separately from successful responses.

\subsection{Traffic Generator}

Requests are sent sequentially from \texttt{h1} via \texttt{curl} with a 0.5\,s
inter-request gap. Each request is timed and its response body is parsed to identify
the serving backend. Three warm-up requests (discarded) populate ARP tables before
the measured phase. The controller readiness check verifies that port 6633 is bound
via \texttt{ss} --- no packets go through the switch, so the algorithm cursor is not
advanced before the first real request. A 5\,s drain period after the last request
allows all flows to expire cleanly.

\subsection{Automated Experiment Runner}

\texttt{scripts/run\_experiment.sh} orchestrates everything:
\begin{enumerate}
\item Clears \texttt{results/}.
\item Prompts for algorithm choice (RR, LC, or both).
\item For each algorithm: cleanup, start Ryu, wait for port 6633, run traffic, drain, stop Ryu.
\item Generate per-algorithm plots (\texttt{plot\_metrics.py}).
\item If both ran, generate comparison plots (\texttt{plot\_comparison.py}).
\end{enumerate}
A full two-algorithm run launches with a single
\texttt{sudo bash scripts/run\_experiment.sh}.

\paragraph{Future improvements.}
The most critical next step is concurrent traffic: multiple parallel \texttt{curl}
processes firing simultaneously. This is where LC is expected to clearly outperform RR.
Adding unequal server weights is another planned extension.
